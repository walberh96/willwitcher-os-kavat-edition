# Kavat fits in 4 GB with LFM3-1.7B

The recommended default model for Kavat is **`lfm3:1.7b-q4_K_M`** (Liquid AI, a 1.1 GB download and about 1.4–1.5 GB loaded), served by Ollama 0.40.13 or later on the RX 6800, with VoiceStudio's speech recognition and synthesis on the CPU. It is the only 2026 candidate designed expressly for local agents with tools and structured output that fits with room to spare next to a good bilingual recognizer inside the 4 GB of the whole assistant; it declares Spanish, it is text-only and Ollama packages it with a native call parser. The recommendation is provisional for one specific reason: its tool-calling figures (BFCL V4 71.39) come from the vendor, the model has been available on Linux for two weeks and nobody independent has compared it yet. That is why the alternatives go in this order: `qwen3.5:2b-q4_K_M` (same generation, the family with the best independent track record), `qwen3:1.7b` (the only one of its size with third-party measurements) and `bonsai-2:4b` (an experimental bet). The small model best measured by third parties, Qwen3.5 4B (87% average on the Home Assistant benchmark), does not fit next to the voice in 4 GB and would only be the default model if the limit counted VRAM alone. No model of this size is reliable on its own with 30 to 60 tools: reliability comes from the design (exact phrases before the model, a short list of tools per request, identifiers in English, validation in the daemon, thinking off). None of this has been run on the real machine and there is no public tool-calling benchmark in Spanish, so the choice is confirmed with a battery of the project's own: about 240 cases in Spanish and English, repeated four times per candidate. Status as of 11 November 2026, with Ollama 0.40.16 as the latest stable version ([Ollama, releases](https://github.com/ollama/ollama/releases)).

## With the voice included, the model is left with between 1.5 and 3 GB

How the limit is read decides more than any engine. Counted as the whole assistant loaded, in VRAM or in RAM, the language model has to be in the 1,000 to 2,000 million parameter class; counted as VRAM only, with the voice on the CPU, a 3B to 4B one would fit. The download size is no use as a budget, because Ollama loads the weights, the context cache and a few hundred MB of buffers: it starts with **4096 tokens of context on cards with less than 24 GiB** and multiplies the reservation by `OLLAMA_NUM_PARALLEL` ([Ollama, context length](https://docs.ollama.com/context-length), [Ollama, FAQ](https://docs.ollama.com/faq)). One project went as far as recording 6.3 GB at run time for a `qwen3:4b` with a 2.6 GB download under its configuration ([ppxai](https://rcconsult.github.io/ppxai/1.17.3/ollama-limitations)). All the memory figures in this report come from file sizes, formulas and other people's measurements; none was taken on an RX 6800.

The voice costs between 1 and 2.5 GB. VoiceStudio runs on the CPU by default on Linux with an AMD card, and its default synthesis engine (OmniVoice on PyTorch) asks for **6 GB of VRAM at minimum**, so it is ruled out ([VoiceStudio, Linux install](https://github.com/debpalash/VoiceStudio/blob/main/docs/install/linux.md), [VoiceStudio, OmniVoice](https://github.com/debpalash/VoiceStudio/blob/main/docs/engines/omnivoice.md)). Its light engines fit: sherpa-onnx dictation on the CPU, with `sherpa-whisper-tiny` (0.104 GB, the default) or `sherpa-parakeet-tdt-v3` (0.67 GB, 25 European languages) ([VoiceStudio, sherpa-onnx](https://github.com/debpalash/VoiceStudio/blob/main/docs/engines/sherpa-onnx-asr.md)); Supertonic-3 (about 400 MB, CPU only, 31 languages; Spanish appears in copies of its model card, not on the VoiceStudio page that was read) or PocketTTS (100 M parameters, six languages including Spanish, gated weights) ([Supertonic-3](https://github.com/debpalash/VoiceStudio/blob/main/docs/engines/supertonic3.md), [copy of the model card](https://huggingface.co/Aliados/supertonic-3), [PocketTTS](https://github.com/debpalash/VoiceStudio/blob/main/docs/engines/pockettts.md)); and OmniVoice GGUF in Q4_K_M (about 659 MB), which today reloads the model on every generation ([OmniVoice GGUF](https://github.com/debpalash/VoiceStudio/blob/main/docs/engines/omnivoice-gguf.md)). For Spanish and English with automatic language detection, Parakeet TDT 0.6B v3 is the best option of those read: NVIDIA declares a **Spanish WER of 3.45% on Fleurs** and the int8 export for sherpa-onnx takes 622 MB of encoder ([NVIDIA, Parakeet TDT v3](https://huggingface.co/nvidia/parakeet-tdt-0.6b-v3), [sherpa-onnx](https://k2-fsa.github.io/sherpa/onnx/pretrained_models/offline-transducer/nemo-transducer-models.html)). The VoiceStudio backend adds about 457 MB before loading any model, according to the project's own measurement on macOS ([VoiceStudio, baselines](https://github.com/debpalash/VoiceStudio/blob/main/docs/performance-baselines.md)).

| Piece | Default choice | Where it runs | Resident memory |
|---|---|---|---|

| Recognition | `sherpa-parakeet-tdt-v3` (int8) | CPU (RAM), VoiceStudio dictation | 0.67 GB on disk; 1–1.5 GB resident, an unmeasured estimate (VoiceStudio warns that peak RAM is "noticeably higher" than the download) |
| Synthesis | Supertonic-3; PocketTTS if voice cloning is wanted | CPU (RAM), VoiceStudio | 0.4–0.5 GB, an estimate from the download |
| VoiceStudio backend | — | RAM | 0.46 GB, measured on macOS without models; the Electron interface is separate and has not been measured |
| **Total** | | **≈1.5 GB in VRAM and 1.9–2.5 GB in RAM** | **≈3.3–4.0 GB** |

The high end brushes the limit, so the order of cuts is fixed in advance: if the real measurement goes over 4 GB, first the recognizer is swapped for `sherpa-whisper-tiny` (probably at the cost of accuracy in Spanish) and only then is the model touched. Conversely, with the minimal voice pair (around 1 GB with the backend) the model would have almost 3 GB, which is what the alternatives with a more expensive cache need.

The split puts the language model on the GPU and all the voice on the CPU. The model goes on the GPU because what decides latency is reading the prompt (instructions, tools and documentation fragments): the RX 6800 processes between 1,380 and 1,680 prompt tokens/s and generates between 80 and 106 tokens/s with a 7B model in Q4_0 under llama.cpp ([ROCm](https://github.com/ggml-org/llama.cpp/discussions/15021), [Vulkan](https://github.com/ggml-org/llama.cpp/discussions/10879)), while there is no measurement of prompt reading on CPU for small models. The voice goes on the CPU because VoiceStudio's dictation already runs there, faster-whisper cannot use an AMD card ([VoiceStudio, faster-whisper](https://github.com/debpalash/VoiceStudio/blob/main/docs/engines/faster-whisper.md)), Parakeet v3 int8 decodes with a real-time factor of 0.03 to 0.3 with two threads ([sherpa-onnx](https://k2-fsa.github.io/sherpa/onnx/pretrained_models/offline-transducer/nemo-transducer-models.html)) and the small synthesis engines are CPU-only. With this split the assistant takes around 1.5 GB of the 16 GB of VRAM and the game keeps the rest. Moving the model to the CPU while gaming (`num_gpu` to 0) is an option to measure, not the starting configuration: a guide that does not state its method gives about 40 tokens/s for Qwen3.5 2B on a Ryzen 7 with DDR5, but the model would compete with the game for cores and memory bandwidth ([insiderllm](https://insiderllm.com/guides/cpu-only-llms-what-actually-works/)).

To serve it, `ollama-vulkan` is the first attempt and `ollama-rocm` the fallback. The RX 6800 is on Ollama's ROCm list for Linux and Vulkan turns on by itself when its backend is installed ([Ollama, GPU](https://docs.ollama.com/gpu)); Arch publishes `ollama`, `ollama-rocm` and `ollama-vulkan` at version 0.40.16-1 ([Arch packages](https://archlinux.org/packages/?q=ollama)). In favor of Vulkan: on that same card it generates around 20% faster in the only comparison available, it takes 40.6 MB installed against 1.3 GB and it does not depend on ROCm, which AMD does not declare compatible with any consumer RX 6000 and which is in transition on Arch (7.2.4 flagged out of date, 10.0 in testing) ([ollama-vulkan](https://archlinux.org/packages/extra/x86_64/ollama-vulkan/), [ollama-rocm](https://archlinux.org/packages/extra/x86_64/ollama-rocm/), [AMD ROCm](https://rocm.docs.amd.com/projects/install-on-linux/en/latest/reference/system-requirements.html), [Arch, rocm-hip](https://archlinux.org/packages/?q=rocm-hip)). Against: on an RX 6600 XT, also RDNA2, Ollama 0.40.8 with Vulkan dropped from 78.5 to 2.64 tokens/s on the second request with the prompt cache enabled, and the issue was closed with no known cause ([issue 19201](https://github.com/ollama/ollama/issues/19201)); a voice assistant lives on short consecutive requests, so this is tested before deciding. With Vulkan, Ollama needs `setcap cap_perfmon+ep` on its binary to read the real VRAM instead of estimating it ([Ollama, GPU](https://docs.ollama.com/gpu)). The MLX tags (`-mlx`, `-nvfp4`) are no use on AMD: outside Apple they only work with NVIDIA ([issue 19369](https://github.com/ollama/ollama/issues/19369)).

The size is kept fixed with four settings: a constant `num_ctx` (8192, Home Assistant's value against Ollama's 4096), `OLLAMA_NUM_PARALLEL=1`, `OLLAMA_KV_CACHE_TYPE=q8_0` (the cache takes roughly half with a very small loss of precision, and it only acts with flash attention) and a single chat model loaded ([Home Assistant, Ollama](https://www.home-assistant.io/integrations/ollama/), [Ollama, FAQ](https://docs.ollama.com/faq)). It is best to leave it resident for the whole session (`keep_alive: -1`, like Home Assistant) and to load it before the game: when VRAM fills up, the `amdgpu` driver evicts buffers to system RAM without telling the game from the rest, and a model with a single layer spilled over loses speed even though it still shows as "100% GPU" ([It's FOSS News](https://itsfoss.com/news/linux-amd-gpu-vram-fix/), [Arch Wiki](https://wiki.archlinux.org/title/Ollama)). In VoiceStudio, `OMNIVOICE_SINGLE_ENGINE_RESIDENT=0` has to be set, because by default it keeps a single engine resident and the recognizer and the synthesizer would be evicted on every turn; with both resident, both count against the budget at the same time ([VoiceStudio, performance](https://github.com/debpalash/VoiceStudio/blob/main/docs/performance.md)). Unloading on idle does not pay off: reloading costs the recognizer 1.3 to 2.5 s and, in the only Ollama measurement on a Radeon of this generation, the first request to a 4B model took 3.35 s against 0.83 s warm ([VoiceStudio, sherpa-onnx](https://github.com/debpalash/VoiceStudio/blob/main/docs/engines/sherpa-onnx-asr.md), [issue 19201](https://github.com/ollama/ollama/issues/19201)).

### If the limit counted only VRAM, the model would go up a class

With this same split the voice already lives in RAM, so counting only VRAM the language model could take the whole 4 GB. The default model would become **`qwen3.5:4b-q4_K_M`** (a 3.3 GB download, of which 676 MB are the vision projector), the small model with the best independent backing: 87.0% average on the Home LLM Leaderboard and 97.5% in a 40-case test with eight tools ([qwen3.5 tags](https://ollama.com/library/qwen3.5/tags), [Home LLM Leaderboard](https://github.com/allenporter/home-assistant-datasets/blob/main/reports/README.md), [jdhodges](https://www.jdhodges.com/blog/local-llms-on-tool-calling-2026-pt1-local-lm/)). The notes contain no measurement of its loaded memory. For the earlier `qwen3:4b` (2.5 GB), the estimate from the cache formula is 3.4 to 3.7 GB with 4096 tokens of context, or with 8192 and a q8_0 cache, which indicates that a 4B fits only just and with a short context ([glukhov.org](https://glukhov.org/llm-performance/optimization/kv-cache-16gb-long-context/)). If Qwen3.5 4B did not fit, the fallback would be `qwen3:4b-instruct`, the default model of Home Assistant's Ollama integration, with 75.4% on that same benchmark ([const.py](https://github.com/home-assistant/core/blob/dev/homeassistant/components/ollama/const.py)). In both readings the voice uses the same RAM, 1 to 2.5 GB; the only thing that changes is whether it counts.

## LFM3-1.7B is the only one built for this job that fits with room to spare

LFM3-1.7B (1,730 million parameters) has had its repository on Hugging Face since 23 October 2026, entered Ollama on the 27th and its GGUF has worked on Linux since version 0.40.13, of 28 October ([LFM3 model card](https://huggingface.co/LiquidAI/LFM3-1.7B), [v0.40.12](https://github.com/ollama/ollama/releases/tag/v0.40.12), [v0.40.13](https://github.com/ollama/ollama/releases/tag/v0.40.13)). The `lfm3:1.7b` tag is a 1.1 GB Q4_K_M GGUF (the Q8_0 weighs 1.8 GB), text-only, with the `tools` and `thinking` badges, its own template generator and parser inside Ollama and a default temperature of 0.1 ([lfm3 tags](https://ollama.com/library/lfm3/tags), [manifest](https://registry.ollama.ai/v2/library/lfm3/manifests/1.7b), [tag page](https://ollama.com/library/lfm3:1.7b)). Liquid describes it almost in the words of Kavat's brief: "designed for local agents, tool calling, structured outputs", with the instruction to use retrieval for knowledge questions and the warning that it is not recommended for programming or for many-step reasoning ([LFM3 model card](https://huggingface.co/LiquidAI/LFM3-1.7B)).

It wins the spot for four reasons, and only the first two have been checked by someone other than the vendor. The first is memory: a third-party blog measured it on Ollama 0.40.14, on CPU, at about **1.4 GB with 4K of context, 1.5 GB with 32K and 1.9 GB with 64K** ([BetterClaw](https://www.betterclaw.io/blog/lfm3-ollama-tool-calling-agent-setup)). It is the only candidate with a measurement that leaves about 2.5 GB for the voice, which is the difference between being able to load Parakeet and having to settle for Whisper tiny, and its context comes almost free, while in Qwen3 1.7B going from 4K to 8K costs about 450 MB of cache according to the formula. The second is that the packaging works: the same test verified that Ollama converts LFM3's XML calls into normal `tool_calls` on both `/api/chat` and `/v1/chat/completions`, and that `think: false` cut a call from 83 to 18 tokens. The third is the fit: it does not drag along the 0.37 to 0.68 GB of vision projector that Qwen3.5 and Bonsai 2 carry, it declares Spanish among its 16 languages and it documents deferred tools (`defer_loading`) so as not to show all the schemas at once ([LFM3 model card](https://huggingface.co/LiquidAI/LFM3-1.7B)). The fourth is its figures, all from the vendor: **BFCL V4 71.39** against 55.12 for Qwen3.5 4B and 48.25 for Gemma 4 E4B, ToolSandbox 80.36 and IFEval 96.66. They have to be read at a discount, because Qwen publishes 50.3 for its own 4B on that same benchmark and NVIDIA's table puts Qwen3.5 4B first among those of its size on BFCL-v3 and Tau2 ([Qwen3.5-4B](https://huggingface.co/Qwen/Qwen3.5-4B), [NVIDIA, Nemotron 3.5 Bolt](https://huggingface.co/nvidia/NVIDIA-Nemotron-3.5-Bolt-E4B-BF16)). Even so, the lead Liquid claims over Qwen3.5 2B (43.6 according to Qwen) is almost 28 points, several times the discrepancy of about 5 points between vendors over the same model ([Qwen3.5-2B](https://huggingface.co/Qwen/Qwen3.5-2B)); this is an inference, not a measurement.

What is missing is exactly what matters most. There is no independent test with a stated method of LFM3-1.7B calling tools, on Ollama or off it; the model has 74,000 downloads on Ollama against 25.2 million for Qwen3.5; and how its architecture behaves on the AMD backends has not been investigated ([lfm3 tags](https://ollama.com/library/lfm3/tags), [qwen3.5 tags](https://ollama.com/library/qwen3.5/tags)). It ships with reasoning on and Liquid warns that turning it off "can be inconsistent" ([LFM3 model card](https://huggingface.co/LiquidAI/LFM3-1.7B)). The family's track record is uneven: `lfm2.5:1.2b` scored 0.920 on Local Agent Bench once its format was parsed properly, but an Ollama contributor diagnosed `lfm2.5-thinking` as "very bad at tool use" ([Local Agent Bench](https://github.com/MikeVeerman/tool-calling-benchmark), [issue 14742](https://github.com/ollama/ollama/issues/14742)). The LFM Open License v1.0 makes commercial use conditional on not exceeding 10 million dollars in annual revenue, which does not affect personal use ([LFM3 license](https://huggingface.co/LiquidAI/LFM3-1.7B/blob/main/LICENSE)).

The starting configuration is the explicit tag `lfm3:1.7b-q4_K_M`, `think: false` on every request, the package's sampling and `num_ctx` 8192. It deserves a second pass with `lfm3:1.7b-q8_0`: in Qwen3-1.7B, 4-bit quantization (NF4, not GGUF) almost tripled the omitted mandatory calls, from 6.0% to 17.3%, while in Qwen3-4B nothing changed, and a 1.7B in Q8 is still smaller than a 4B in Q4 ([NeurIPS 2026, poster 171153](https://neurips.cc/virtual/2026/171153)).

## Two Qwens as fallbacks, a ternary bet and the discards

| Order | Tag | Download | When it makes sense | What backs it |
|---|---|---|---|---|
| 1 | `qwen3.5:2b-q4_K_M` | 1.9 GB (1.3 GB of model and 671 MB of vision projector) | If LFM3 fails the battery in Spanish or gives trouble for being new on Linux; if vision is wanted later, or an Apache 2.0 license | Vendor figures only: BFCL-V4 43.6, TAU2 48.8, IFEval 78.6 ([Qwen3.5-2B](https://huggingface.co/Qwen/Qwen3.5-2B)); its 4B sibling is the best-measured small model |
| 2 | `qwen3:1.7b` | 1.4 GB | If behavior already measured by third parties is preferred; it requires the minimal voice pair (about 2.2–2.5 GB loaded with 4K of context, an estimate) | Official BFCL: 74.6% on "live" cases, 76.5% abstention, 11% on multi-turn ([BFCL](https://gorilla.cs.berkeley.edu/data_overall.csv)); first on Local Agent Bench with 0.960 ([repository](https://github.com/MikeVeerman/tool-calling-benchmark)); 36.7% on TinyToolBench ([repository](https://github.com/SonuDKing2721/TinyToolBench)) |
| 3 | `bonsai-2:4b` | 1.6 GB (1.2 GB of model and 367 MB of projector) | A bet: it is Qwen3.5 4B with ternary weights; it is adopted only if it wins the battery | Vendor claim: "close to full-precision quality" ([bonsai-2](https://ollama.com/library/bonsai-2)); no independent test |
| 4 | `qwen3.5:4b-q4_K_M` | 3.3 GB | Only if the limit counts VRAM alone | 87.0% on the Home LLM Leaderboard; 97.5% in 40 cases with LM Studio |
| 5 | Fine-tuning a 1.7B on the project's own catalog | The base model's | Second step, if no stock model reaches the threshold | Qwen3-1.7B: from 75.0% to 89.8% on the easy set of Home Assistant ([hua](https://github.com/nk3750/hua)) |

The order reflects what gets tested first if LFM3 fails. Qwen3.5 2B is the natural replacement because it shares generation, license and parser with the best-measured small model, and Ollama fixed its call parsing in three releases over the course of 2026 ([v0.17.3](https://github.com/ollama/ollama/releases/tag/v0.17.3), [v0.17.6](https://github.com/ollama/ollama/releases/tag/v0.17.6), [v0.19.0](https://github.com/ollama/ollama/releases/tag/v0.19.0)). It has three drawbacks. The tag `2b-q4_K_M` has to be named, because plain `qwen3.5:2b` is a 2.7 GB Q8_0 ([qwen3.5 tags](https://ollama.com/library/qwen3.5/tags)). A third of its download is a vision projector that Kavat does not use, and it has not been verified whether Ollama leaves it out of memory when no images are sent. And its model card presents it for prototypes, fine-tuning and research; Qwen also warns of loops in thinking mode in its smallest sizes ([Qwen3.5-2B](https://huggingface.co/Qwen/Qwen3.5-2B), [Qwen3.5-0.8B](https://huggingface.co/Qwen/Qwen3.5-0.8B)). Two open issues affect it: the Qwen3.5 parser returns `arguments: {}` when the model writes the arguments as JSON inside `<function=...>`, and Ollama's VRAM prediction overcounts the cache of hybrid models like Qwen3.5 by 4 to 8 times ([issue 19650](https://github.com/ollama/ollama/issues/19650), [issue 19463](https://github.com/ollama/ollama/issues/19463)).

Qwen3 1.7B is from 2025, but it is the only model of its class with third-party measurements, and those measurements show the ceiling of the whole class: it gets single commands right, it abstains reasonably and it collapses as soon as chaining is needed (0 of 27 chains on TinyToolBench). Bonsai 2 4B is the option with the most potential and the least evidence: if it really keeps the quality of Qwen3.5 4B in 1.6 GB, it would be the best model that fits, but it only exists in `q2_0` quantization, it inherits the Qwen3.5 parser with its faults, and nobody has checked either its tool calling or its ternary kernels on an AMD card ([bonsai-2 tags](https://ollama.com/library/bonsai-2/tags), [manifest](https://registry.ollama.ai/v2/library/bonsai-2/manifests/4b)).

| `tev1` and the decision models; `deepseek-r1:1.5b` | The former return probabilities, not calls ([tev1](https://ollama.com/library/tev1)); the latter carries its family's `tools` badge without having a tools section in the template ([manifest](https://registry.ollama.ai/v2/library/deepseek-r1/manifests/1.5b)) |

## The design around the model matters more than the model

The independent tests agree on where models under 4B fail: multi-step chains, exact arguments, call-shaped text that the server does not recognize, and acting when it was not called for ([TinyToolBench](https://github.com/SonuDKing2721/TinyToolBench), [Local Agent Bench](https://github.com/MikeVeerman/tool-calling-benchmark)). Each piece of the design attacks one of those failures.

### Exact phrases handle the frequent requests without a model

Home Assistant handles commands first with exact phrases and with its intent matcher, and only sends the model what it does not understand ([Home Assistant, blog](https://www.home-assistant.io/blog/2025/09/11/ai-in-home-assistant/)). That model-free matcher resolves on its own **65.3% of the easy set** of its benchmark, and in an integration tuned for 8 GB the common commands that skip the model respond in about 0.05 s against medians of 2.9 to 3.6 s through the model ([hometiny](https://github.com/DylanGerloski/hometiny/blob/main/CARD.md), [8 GB integration thread](https://community.home-assistant.io/t/integration-tuned-for-running-assist-on-a-local-llm-in-8-gb-vram/1025725)). Open Voice OS and Leon order things the same way: the deterministic first ([OVOS](https://openvoiceos.github.io/ovos-technical-manual/153-persona_pipeline), [Leon](https://github.com/leon-ai/leon)). For Kavat, "turn up the volume", "dark theme" or "open Firefox" must be resolved with a phrase table per language, with optional words and alternatives in the style of Home Assistant's sentence triggers, and the model is left for what the table does not cover ([sentence triggers](https://www.home-assistant.io/triggers/conversation/)).

### Five to eight tools per request, not sixty

Showing the 30 to 60 tools at once is the most expensive mistake. Measured on small models: Qwen2.5-1.5B drops from 55.2 to 29.5 when the list is widened to 20 functions and Qwen2.5-3B from 59.9% to 43.3% when going from 10 to 50; narrowing the list beforehand gives 26 points back to the 1.5B and 11 to the 3B ([Tool-DC](https://arxiv.org/html/2603.11495v1)). Selecting beforehand with a tiny embedding model works: MiniLM placed the correct tool among the top five in **97.5% of 370 queries** from BFCL, and in TinyAgent embedding retrieval found 94.9% of the needed tools with three candidates and 96.8% with six ([arXiv 2605.24660](https://arxiv.org/html/2605.24660v1), [TinyAgent](https://arxiv.org/html/2409.00608v3)). The rule for Kavat is to show five to eight tools chosen by similarity and leave an escape route when similarity is low (a widened list or a "there is no tool for that" answer), as Less-is-More does when it goes back to the full list below 0.5 ([Less is More](https://arxiv.org/html/2411.15399v1)). There are three caveats. Retrieval becomes the ceiling, because if it fails the model cannot recover. Nobody has measured this selection in Spanish, so each tool must be indexed with aliases in both languages. And the embedding model also takes memory that counts against the 4 GB and that the notes do not quantify. In addition, Ollama silently discards calls to functions that are not in the request's list (28 of 32 repetitions with `qwen3:8b`), so an empty response with generated tokens must be treated as a failure and retried with the widened list ([issue 19187](https://github.com/ollama/ollama/issues/19187)).

### English on the inside, Spanish on the outside, and the daemon validates

Tool names, descriptions and enumerated values go in English even if the user speaks Spanish. In an Arabic-English study on BFCL, English descriptions won 322 comparisons against 37 and queries in Arabic cost 5 to 10 points on average ([arXiv 2601.05101](https://arxiv.org/html/2601.05101v1)); in the multilingual extension of BFCL, the dominant failure was copying the value in the user's language into an argument that expected a canonical identifier ([arXiv 2601.05366](https://arxiv.org/html/2601.05366v1)). Spanish is much closer to English than Arabic is, so that penalty is probably a ceiling, but it is an extrapolation. The remedy is in the design: arguments with closed enumerations, normalization in the daemon of whatever arrives in Spanish and validation of everything before executing (that the name exists, that the types and ranges match, that the application or the package exists). Google asks for exactly this for Gemma 4, "Always validate function names and arguments before execution", and the typical failure of the smallest models is not broken JSON but naming things that do not exist: a 35 MB model did it in 168 of 196 requests ([Gemma 4, function calling](https://ai.google.dev/gemma/docs/capabilities/text/function-calling-gemma4), [hometiny](https://github.com/DylanGerloski/hometiny/blob/main/CARD.md)).

### Native calls, no thinking and a single step

Calls are requested through Ollama's native `tools` field and without `format`. Constrained decoding guarantees valid JSON and nothing more: in a study with models from 0.5B to 1.7B, forcing the schema raised validity to 100% but lowered the executable accuracy of a calendar task **from 91.5% to 48.0%** ([arXiv 2605.26128](https://arxiv.org/abs/2605.26128)), and in Ollama models cannot call tools when `format` is `json` ([issue 18944](https://github.com/ollama/ollama/issues/18944)). Thinking is set explicitly on every request, because each model comes with a different default, and it is turned off for voice: Home Assistant ships it off and the best small rows of its benchmark were measured that way ([Home Assistant, Ollama](https://www.home-assistant.io/integrations/ollama/), [Leaderboard](https://github.com/allenporter/home-assistant-datasets/blob/main/reports/README.md)). Turning it off has a cost that the battery must measure: in one study, Qwen3-4B with thinking beat the version without thinking in 96 of 112 comparisons, and the best model of 4B or less on the official BFCL is one that thinks, in exchange for 13.5 s of average latency against 7.6 s ([arXiv 2601.05101](https://arxiv.org/html/2601.05101v1), [BFCL](https://gorilla.cs.berkeley.edu/data_overall.csv)). A reasonable way out is to reserve it for the second attempt at an ambiguous request. `num_predict` has to be limited so that a stuck reasoning does not block the turn (one integration recorded an 18.9 s wait before setting a cap), but with slack, because a call cut off by that limit returns an HTTP 500 ([8 GB integration thread](https://community.home-assistant.io/t/integration-tuned-for-running-assist-on-a-local-llm-in-8-gb-vram/1025725), [issue 19493](https://github.com/ollama/ollama/issues/19493)). And each command must be resolved with a single call: a compound "skill", such as switching mode, must be a single typed tool whose steps the daemon executes, because chaining is exactly what these models do not do.

The daemon, not the model, says what happened. Small models claim actions they have not executed; in the 8 GB integration, a single re-run when the model said it had acted without calling anything took repeated commands from 0 of 24 to 24 of 24. The spoken confirmation must come from the tool result, with a cap of three identical calls in a row ([ppxai](https://rcconsult.github.io/ppxai/1.17.3/ollama-limitations)). Tools that are hard to undo, such as installing a package, must ask for confirmation; it is a precaution, because no project has measured how much it reduces errors. Tool results and documentation fragments are treated as data: Gemma 4 E4B resisted 6 of 6 injections with a simple prompt and only 2 of 6 through the tool route ([field report](https://mpklu.github.io/posts/gemma-4-benchmark)). Questions about the machine are answered only with fragments retrieved from the documentation and in a request without tools: Home Assistant documents that small models do not hold a conversation well with tools attached and proposes two configurations of the same model, one with them and one without ([Home Assistant, Ollama](https://www.home-assistant.io/integrations/ollama/)). In the voice loop, sending the text to synthesis as it is generated cut the time to first audio from 5.31 s to 0.56 s in Home Assistant's local stack ([Home Assistant, blog](https://www.home-assistant.io/blog/2025/09/11/ai-in-home-assistant/)).

### The model is changed by contract, not by name

Making the model configurable forces the contract to be defined. A valid entry is a tag from Ollama's official library with the `tools` capability, written with its quantization explicit (several default tags are Q8_0) and accompanied by its profile: `think`, `num_ctx`, temperature and shortlist size. The `tools` badge is per family and guarantees nothing per tag, and a GGUF imported without Ollama's parser can lose tools altogether ([deepseek-r1 manifest](https://registry.ollama.ai/v2/library/deepseek-r1/manifests/1.5b), [hometiny](https://github.com/DylanGerloski/hometiny/blob/main/CARD.md)). Kavat must query `/api/show` when changing model to read its capabilities and thinking values, and every change must pass the battery again ([v0.34.3](https://github.com/ollama/ollama/releases/tag/v0.34.3)).

### Fine-tuning is the second step

If no stock model reaches the threshold, the next step is not a bigger model but fine-tuning on the project's own catalog, the lever with the largest measured effect: Qwen3-1.7B went **from 75.0% to 89.8%** on the easy set of Home Assistant, and models from 270M to 350M reach 91–98% on narrow tasks according to a provider's study ([hua](https://github.com/nk3750/hua), [distil labs](https://www.distillabs.ai/learn/qwen-vs-llama-vs-gemma-for-tool-calling/)). The published runs with good results used between 5,000 and 13,000 synthetic examples; with 500, a 350M model only went from 28% to 47%, and abstention does not improve if the data has no negative examples ([TinyToolCaller](https://app.readytensor.ai/publications/tinytoolcaller-qlora-fine-tuning-of-a-15b-llm-for-reliable-function-calling-a95jlwdioKYatbzl8OKNS), [community FunctionGemma LoRA](https://huggingface.co/sumitagrawal/functiongemma-270m-tool-agent/blob/main/README.md), [Liquid, home assistant example](https://docs.liquid.ai/examples/customize-models/home-assistant.md)). The cost is rigidity, because adding a tool forces retraining, and deployment: Ollama removed adapter import from its documentation in version 0.34.1, so the LoRA has to be merged, converted to GGUF and quantized with the llama.cpp tools ([v0.34.1](https://github.com/ollama/ollama/releases/tag/v0.34.1), [import guide](https://docs.ollama.com/import.md)).

## The choice is confirmed with about 240 cases of the project's own, repeated four times

No public figure answers Kavat's question: the independent generic tests use 3 to 8 tools, none is in Spanish, none includes LFM3-1.7B or Qwen3.5 2B and none declares having been run on a Radeon. Besides, a model's score is a property of the combination of model, quantization, template, server version and thinking setting: Qwen3-1.7B scores 60.2% or 75.0% on the same easy set depending on the run ([Leaderboard](https://github.com/allenporter/home-assistant-datasets/blob/main/reports/README.md), [hua](https://github.com/nk3750/hua)).

The battery copies the shape of the Home Assistant datasets (sentences, initial state and expected state change) and Liquid's taxonomy (capability, way of asking and depth of inference), with deterministic checkers and no judge model ([assist dataset](https://github.com/allenporter/home-assistant-datasets/blob/main/datasets/assist/README.md), [Liquid](https://docs.liquid.ai/examples/customize-models/home-assistant)). For a catalog of 40 tools that is **about 240 distinct cases**: 160 direct ones (each tool with two phrasings in Spanish and two in English, varying between imperative, colloquial, implicit and question), 40 in which nothing must be called (out of scope, ambiguous, keyword traps, tasks that are for Claude), 20 with mixed languages or typical transcription errors and 20 questions about the documentation, half of them with no answer in it. With 30 tools that comes to about 200 cases and with 60 about 320. Each case is run **four times** with the real sampling, as assist-mini does, whose 196 executions give intervals of ±4 to ±7 points; Toolery, with 715 executions, treats differences of less than 2 points as noise ([assist-mini dataset card](https://github.com/allenporter/home-assistant-datasets/blob/main/datasets/assist-mini/dataset_card.yaml), [Toolery](https://forums.developer.nvidia.com/t/toolery-0-1-0-a-deterministic-tool-calling-benchmark-for-local-llms/371794)). That is between 800 and 1,280 executions per configuration, and a run of 196 takes about 7 minutes on an RTX 3060, so each configuration costs tens of minutes, not hours ([hua](https://github.com/nk3750/hua)). The split and the number of cases are a proposal of this report built on those precedents.

Four things are measured separately, because lumping them together hides the failure. Accuracy: valid call, correct tool, correct arguments, valid but wrong call, correct abstention and correct answer to the documentation questions ([arXiv 2605.26128](https://arxiv.org/abs/2605.26128)). Serving failures as a category of their own: HTTP 4xx or 5xx, empty response with generated tokens, reasoning-only response and call-shaped text ([arXiv 2609.26693](https://arxiv.org/abs/2609.26693)). Latency: time to first token, to completed action and to first audio, plus cold and warm `load_duration` and the speed of the second consecutive request, which is where the Vulkan drop would show up ([issue 19201](https://github.com/ollama/ollama/issues/19201)). And memory: `ollama ps` and `/api/ps` (fields `size` and `size_vram`), `amdgpu_top` and the resident memory of the VoiceStudio process tree, with both voice engines loaded and with a game running, loading the assistant before and after the game, and noting the effect on frame times while the model generates ([Ollama, ps API](https://docs.ollama.com/api/ps.md), [Arch Wiki](https://wiki.archlinux.org/title/Ollama)).

The configurations to compare are `lfm3:1.7b-q4_K_M`, `lfm3:1.7b-q8_0`, `qwen3.5:2b-q4_K_M`, `qwen3:1.7b` and `bonsai-2:4b`, each with thinking off and on, plus three controls: a frontier model to validate the harness ("If a state-of-the-art model does not pass almost everything, the problem is your code, not the model"), the phrase table alone as a model-free baseline and `qwen3.5:4b-q4_K_M` as a ceiling even though it does not fit ([Liquid](https://docs.liquid.ai/examples/customize-models/home-assistant), [hometiny](https://github.com/DylanGerloski/hometiny/blob/main/CARD.md)). Each run is declared before launching it and the Ollama version, the tag, the template and the settings are noted down ([serving-stack confounds](https://agentpatterns.ai/patterns/anti-patterns/serving-stack-confound-tool-call-evaluation/)). promptfoo, DeepEval and Inspect can point at Ollama, but promptfoo's documented assertion only validates the schema; checking tool and arguments requires custom assertions or DeepEval's parameter-matching mode ([promptfoo](https://www.promptfoo.dev/docs/providers/ollama), [DeepEval](https://deepeval.com/docs/metrics-tool-correctness), [Inspect](https://inspect.aisi.org.uk/providers.html)).

The decision rule is this report's judgment, not a published threshold. LFM3 stays if the whole set fits in 4 GB measured with the game open, if it does not execute any wrong destructive action and if it is not more than 4 points below the best alternative that fits; with smaller differences, latency and memory decide. As a reference for what is achievable, Qwen3.5 4B scores 88.3% on the easy set of Home Assistant and a tuned 1.7B 89.8%; if the full configuration (phrase table, shortlist and model) does not reach that zone on the direct cases, the next step is fine-tuning. The voice is tested separately with the project's own recordings in both languages, because there is no published Spanish WER for the alternatives to Parakeet either.

## Conclusion

The constraint that rules is not the card but the definition of the limit. With the recommended split, the assistant uses around 1.5 GB of a 16 GB GPU, and what prevents moving up to a 4B model, the jump that the independent benchmarks do back, is the voice's RAM counted inside the 4 GB. Relaxing the limit to "4 GB of VRAM" would be a one-line configuration change with more likely effect than any tuning of the small model.

What lasts is not the model's name but the battery and the contract. The model recommended today has been on Linux for two weeks, and the small class is renewed every few months: whoever keeps 240 cases of their own can re-evaluate each newcomer in an afternoon. Three events would change this recommendation: the first independent test of LFM3-1.7B, the maturing of `lfm3-audio`, which shares the same language model and could merge recognition, agent and synthesis in 1.7 GB when its voice stops being English-only, and the arrival of the resident OmniVoice GGUF server in VoiceStudio, which is not distributed today ([lfm3-audio](https://registry.ollama.ai/v2/library/lfm3-audio/manifests/2b), [VoiceStudio, releases](https://github.com/debpalash/VoiceStudio/releases)).
